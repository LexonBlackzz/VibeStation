# VibeStation v0.5.2-definitive UI Overhaul Plan

## Intent

Create a full UI overhaul for VibeStation that closely follows the supplied 1280x800 reference: a dark, nostalgic PS1-era launcher built around the provided clean room/background image, while keeping the emulator core and existing runtime behavior isolated from the presentation rewrite.

This branch starts from `main`. No emulator-core behavior should change as part of the first UI pass.

## Design target

The new home screen should treat 1280x800 as the reference design canvas.

Key visual elements:

- Full-window supplied background image, centered and scaled with aspect preservation.
- Dark readability treatment over the left side and lower information region.
- Large `VibeStation` wordmark in the upper-left.
- Four small PS1-inspired color bars beneath the wordmark.
- `PS1 EMULATOR` subtitle and short stacked tagline.
- Vertical primary navigation:
  - Start Emulation
  - Load Game
  - Change BIOS
  - Settings
  - Exit
- Large outlined selection/focus treatment matching the reference.
- Thin, monochrome line icons for primary actions.
- Upper-right version text and small tagline.
- Bottom-left Game Library panel.
- Bottom-right System Info panel.
- Dark translucent panels with restrained borders instead of standard ImGui desktop windows.

The interface should feel like a purpose-built frontend rather than a collection of developer/debug ImGui windows.

## Functional mapping

The visual rewrite should reuse the existing application logic instead of duplicating emulator behavior.

- **Start Emulation** -> existing BIOS boot flow via `start_bios_from_ui()`.
- **Load Game** -> existing disc selection / library flow and `load_disc_from_ui(...)`.
- **Change BIOS** -> existing BIOS file picker/config path.
- **Settings** -> existing settings state and settings panels, presented through the new shell.
- **Exit** -> request application shutdown cleanly.
- **Game Library** -> existing `rom_directory_`, `game_library_`, `refresh_game_library()`, and selected-game boot path.
- **System Info** -> existing BIOS/config/runtime state, with no new emulator dependencies.

Debug and diagnostics panels remain available, but should no longer dominate the default home experience.

## Architecture

Keep emulator state in `App`, but move most new presentation code out of the already-large `src/ui/app.cpp`.

Planned files:

- `src/ui/definitive/definitive_home.h`
- `src/ui/definitive/definitive_home.cpp`
- `src/ui/definitive/ui_texture.h`
- `src/ui/definitive/ui_texture.cpp`
- `resources/ui/definitive/background.png`
- optional `resources/ui/definitive/fonts/` if a bundled mono font is needed

The home renderer should receive only the state/actions it needs rather than owning emulator objects.

## Implementation phases

### Phase 1 — Asset and rendering plumbing

- Add the supplied clean 1280x800 background image to `resources/ui/definitive/`.
- Add a small OpenGL texture loader suitable for UI assets.
- Load/release the background texture with the SDL/OpenGL UI lifetime.
- Add helpers for:
  - reference-canvas coordinates
  - DPI-aware scaling
  - background cover/contain calculations
  - translucent panel drawing
  - thin border/highlight drawing

Acceptance:
- A static home screen can render the supplied background correctly at 1280x800 and resize without stretching.

### Phase 2 — Definitive home shell

- Replace the current default desktop-like home presentation with a single full-window ImGui canvas.
- Recreate the reference composition:
  - wordmark
  - color bars
  - subtitle/tagline
  - primary navigation
  - version/tagline block
  - Game Library panel
  - System Info panel
- Draw most decoration through `ImDrawList` so the UI does not inherit normal ImGui-window chrome.
- Preserve keyboard/controller focus visibility.

Acceptance:
- At 1280x800, the layout should visually track the supplied reference closely.

### Phase 3 — Primary navigation behavior

Wire the new buttons to existing behavior:

- Start Emulation
- Load Game
- Change BIOS
- Settings
- Exit

Add:
- mouse hover/press
- keyboard navigation
- controller navigation
- animated focus interpolation kept subtle and fast

Acceptance:
- Every top-level action works without needing the legacy menu bar.

### Phase 4 — Game Library redesign

- Keep the current ROM-directory scan and game discovery logic.
- Show directory state and game count in the bottom-left panel.
- Empty state:
  - `ROM Directory: not set`
  - warning
  - Set Directory
  - Refresh
- Populated state:
  - compact scrollable game list
  - selected game state
  - launch action
- Avoid scanning every frame; retain the current dirty/refresh behavior.

Acceptance:
- Existing library behavior survives the UI rewrite with no compatibility regression.

### Phase 5 — Settings and secondary panels

- Rehost the existing settings UI in a modal/overlay or dedicated full-screen subview styled consistently with the new shell.
- Keep advanced/debug panels available through a secondary/advanced area.
- Preserve:
  - input bindings
  - audio
  - system
  - memory cards
  - performance/debug tools
  - experimental tools
  - Discord presence settings

Acceptance:
- No existing setting becomes unreachable.

### Phase 6 — Emulator-running transition

- Home shell is the launcher state.
- Once emulation is active, transition cleanly to the emulator display.
- Existing emulator screen, overlays, and debug panels continue to work.
- Provide an obvious route back to the launcher/settings without stopping emulation unless the user chooses to.

Acceptance:
- UI overhaul does not disturb emulation timing or renderer ownership.

### Phase 7 — Window chrome and polish

After the shell is stable:

- Evaluate borderless/custom window chrome on Windows to better match the reference.
- If adopted:
  - custom minimize/maximize/close controls
  - draggable title region
  - correct maximize/restore behavior
  - no interference with SDL input
- Add final typography, spacing, icon and hover-state polish.
- Keep effects inexpensive; no mandatory real-time blur.

Acceptance:
- The frontend looks intentional at 1280x800 and remains usable on resized/high-DPI windows.

## Responsive rules

- 1280x800 is the pixel-reference layout.
- Never non-uniformly stretch the background.
- Maintain a safe left navigation zone and bottom information zone.
- On smaller windows, reduce spacing/font sizes before hiding information.
- On very small windows, allow lower information panels to collapse before the main actions become unusable.
- On ultrawide windows, keep the composition anchored around the reference canvas instead of spreading controls excessively.

## Styling notes

- Palette: near-black, cool gray, soft white, with restrained PS1 red/teal/gold/blue accents.
- Typography: primarily mono/technical; avoid glossy modern UI styling.
- Borders: thin, low-contrast gray; bright white/blue-white only for active focus.
- Motion: short opacity/position easing only; avoid flashy transitions.
- Background remains visually dominant on the right side.

## Versioning

The branch is named `v0.5.2-definitive`.

During implementation, update visible app/version text consistently rather than hard-coding a separate UI-only version. The current `main` branch reports `v0.6.0-dev`, so version metadata should be reconciled deliberately when implementation begins.

## Regression constraints

Do not change in the UI-overhaul work unless strictly necessary:

- CPU/GPU/SPU behavior
- BIOS loading semantics
- disc parsing/boot behavior
- timing
- renderer output
- save-state/rewind behavior
- memory-card format
- input emulation semantics

The goal is to make the frontend definitive without turning a presentation rewrite into an emulator-core rewrite.

## First implementation milestone

The first implementation milestone should be intentionally narrow:

1. add the clean background asset,
2. render it as the full launcher background,
3. render the upper-left branding and five primary navigation items,
4. make the five actions functional,
5. leave the deeper library/settings restyle for the next pass.

That gives a visually recognizable new VibeStation shell early without destabilizing the rest of the application.
